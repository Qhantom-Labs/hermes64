# Hermes64 Studio in Hermes Desktop: install, rollback, keyboard

Verified on a real Hermes Desktop: a second, throwaway instance of the same build the owner runs
(`apps/desktop/dist`, identical `hermes-build.json` to `release/mac-arm64/Hermes.app`, Electron 44.9.3)
with a private HOME, HERMES_HOME and Electron profile under `cache/scratch`. Never in the owner's daily app
or profile. Commands, outputs and screenshots: `DESKTOP-RESULT.md`. Claims taken from host source but
not exercised are marked *(source)*.

This supersedes the "intended steps, not yet run" and "mock host" parts of `docs/STUDIO-INSTALL.md`
(that file sits outside this lane's paths and was left for the merge lane).

## How the desktop contribution is delivered

`hermes64` is a unified agent + desktop package. One folder holds:

| Path | Role |
|---|---|
| `plugin.yaml`, `__init__.py`, `adventure_maker/` | agent half (13 tools + `/hermes64`). Loads with no Desktop present (CLI check in `DESKTOP-RESULT.md`). |
| `plugin.yaml` `config_schema` | rendered by Desktop as **Settings ▸ Plugins ▸ Hermes64 Studio** (Projects root, Bundle root, Python/Blender/Godot paths). |
| `dashboard/manifest.json` + `dashboard/plugin_api.py` | backend routes under `/api/plugins/hermes64/studio/*`, the plugin's own namespace (`ctx.rest` reaches nothing else). Mounted at gateway start, only when `hermes64` is in `plugins.enabled`. |
| `desktop/plugin.js` | desktop half: one uncompiled ES module importing only `@hermes/plugin-sdk`, `react`, `react/jsx-runtime`. Generated by `studio/tools/sync_shared.py` from `studio/prototype/**` + `studio/plugin/glue.js`; edit those, not this file. |

Observed on disk: Desktop copies the package's `desktop/` folder to `<HERMES_HOME>/desktop-plugins/hermes64/`
(`plugin.js` byte-identical to the checkout's) with a marker
`.hermes-package.json` = `{"package": "hermes64", "source": ".../plugins/hermes64/desktop", "sourceMtimeMs": …, "linked": true}`.
Because it belongs to a package, the desktop half ships **opt-in**: listed Off in Capabilities ▸ Plugins until
the owner switches it on.

Registered through the SDK (nothing runs at load except registration):

| Contribution | SDK area | Data |
|---|---|---|
| Studio page | `ROUTES_AREA` | `{ path: '/hermes64-studio' }`: a React route in the host document (no iframe, no webview) |
| "Studio" sidebar row | `SIDEBAR_NAV_AREA` | `{ path: '/hermes64-studio', label: 'Studio', codicon: 'game' }` |
| STUDIO tab, third after SESSIONS and BOTS | `PANES_AREA` | `{ placement: 'left', width: '260px', collapsible: true, hideOnly: true, tabTitleText: () => 'Studio', dock: { pane: 'sessions', pos: 'center' } }`: same chrome as the built-in Bots tab |

Host calls used: `ctx.rest` (own backend), `ctx.os.revealPath` (Open folder), `ctx.os.writeClipboard`
(fallback only), `ctx.storage`, `host.navigate`, `host.newChat`, `host.composer.setDraft('new', …)` +
`host.composer.focus('new')` (NEW GAME; never `submit`), `host.notify`/`notifyError`, `SandboxedFrame` (web builds).

## Install (the owner runs this; it includes one backend restart)

1. **Link the package** (development) or install it as usual:
   ```bash
   ln -s /path/to/hermes64-checkout ~/.hermes/plugins/hermes64
   ```
2. **Allow the agent + backend half** in `~/.hermes/config.yaml`:
   ```yaml
   plugins:
     enabled:
       - hermes64
   ```
3. **Restart the Hermes backend** so the backend routes mount. This is the only restart, and it is the owner's call.
4. **Switch the desktop half on:** **Capabilities ▸ Plugins**, search `hermes64`, switch **Hermes64 Studio** On.
   The STUDIO tab and the Studio row appear at once, with no app restart.
5. **Choose the projects folder:** the gear on the card (**Settings: Hermes64 Studio**) or
   **Settings ▸ Plugins ▸ Hermes64 Studio ▸ Projects root**: an absolute, existing folder, then
   **Save settings**. It is the same key the tools read (`plugins.entries.hermes64.settings.projects_root`).
6. **Open it:** the **Studio** row, or the **STUDIO** tab (Enter on a game opens the page on it).

First open shows the games as box cards, or NEW GAME alone for an empty folder. If no folder is set,
the folder is missing or the backend is off, the shelf says "Can't read the shelf" with one sentence
naming the fix, and offers ENTER Try Again.

## Roll back (one step, no restart)

- **Remove just the Studio:** open the card in **Capabilities ▸ Plugins** and switch its **Desktop**
  half (`Desktop: Hermes64 Studio`) **Off**. The STUDIO tab, the Studio row, the route and the rack
  vanish immediately. The agent tools keep working (`config.yaml` stays byte-identical). Switching
  it back On restores the Studio. Both directions were verified.
- **Turn the whole package off:** the card's main switch **Off**. This also removes the Studio at once
  (verified) and turns the agent half off. Switching the card back **On** re-enables the agent half
  through the host's own activation, which prepares dependencies for the data root. In the
  network-blocked sandbox that step failed with the host's error "Could not toggle hermes64: … uv sync …"
  in 2 of 3 runs, and the tab did not come back in those runs. To bring back only the tab, use the
  Desktop switch above.
- **Remove completely:** take `hermes64` out of `plugins.enabled`, restart the backend, and delete
  the `~/.hermes/plugins/hermes64` link. Desktop then drops its `desktop-plugins/hermes64` copy *(source)*.

Unmounting the page calls the same eject that stops a running play server (`studio/plugin/glue.js`).
The harness verifies that eject stops the server. The rollback runs did not have a game playing.

## Keyboard, and how it shares keys with the host

The Studio reads keys only while it has focus. Its listeners sit on its own root, never on `window`.
Checked against the host source (`apps/desktop/src/lib/keybinds/*`, `app/hooks/use-keybinds.ts`)
and on the real host:

| Where | Keys | Host interaction |
|---|---|---|
| Studio page | ←/→ move, Shift+←/→ page, Home/End, Enter/Space open, Esc/Backspace back, Tab menu, Q/E or [/] filter, / find, ? help, M sound | The page is a host page route (`$workspaceIsPage`), so the host's type-to-focus, soft `/` and Enter, Esc-to-stop and Enter/Esc approval keys stand down there by design. |
| Studio page | PageUp/PageDown | **Host-owned** (`conversation.scrollPageUp/Down`, capture phase). The Studio yields any key the host already claimed (`defaultPrevented`), so Shift+←/→ pages instead, and the help card says so. |
| Studio page | Shift+X | Host-owned (`appearance.toggleMode`). The Studio does not use X. |
| Playing a web build | the game's own keys; **hold Esc 0.6 s** to eject | A real Godot build focuses its canvas inside the out-of-process `SandboxedFrame`, so neither the Studio nor the Desktop receives any key while it plays. The play server adds a small bridge to the export's entry page only: holding Esc posts one fixed message, and the Studio accepts it only from its own frame. A short Esc stays with the game (pause menus). After eject the keyboard returns to the Studio. |
| STUDIO tab (rack) | ↑/↓, Home/End move (focus follows), Enter/Space open | Rows are `role="treeitem"` with one roving tab stop. Letters and Esc stay with the host (type-to-focus, Esc-to-stop), exactly as on the Sessions list. |

Fixed in this lane after the real host showed the problem:
- The rack used `role="listbox"` and the detail actions used `role="menu"`. The host treats any
  `[role=listbox|menu|dialog|alertdialog]` in the document as an open overlay (`OVERLAY_SURFACE`, a bare
  `document.querySelector`). The mounted STUDIO tab therefore switched off type-to-focus, soft `/` and
  Enter, Esc-to-stop and the approval keys across the whole app. The rack is now a tree and the actions
  are a labelled group of buttons, and a test now fails if any overlay role appears in the bundle.
- A real web build trapped the keyboard: Esc never reached the Studio. The fix is the hold-Esc bridge.
- The game frame covered the EJECT label. The play screen is now sized from the Studio's own box and
  sits below the eject band.
