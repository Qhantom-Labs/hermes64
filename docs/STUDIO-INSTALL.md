# Hermes64 Studio: install, disclosure, and what is untested

**Status (MERGE4).** This is the first Studio lane's design and disclosure document. The desktop half has since been verified in a real Hermes Desktop (a throwaway isolated instance, never the owner's app): the current install and rollback steps are `docs/studio/DESKTOP-INSTALL.md`, and what ran on the real host, what it found and what is still unverified are in `docs/studio/DESKTOP-RESULT.md`. The cover tool's adopted box art on the shelf was verified the same way (`docs/MERGE4-LOG.md` section 5). The "mock host" and "Not tested in the real app" sections below are kept as the original record.

## What ships

The Studio rides inside the existing `hermes64` plugin package as a unified package (agent half, backend half and desktop half in one folder):

| Path in the package | Role |
|---|---|
| `plugin.yaml`, `__init__.py`, `adventure_maker/` | the existing agent half (tools), unchanged except for the new read-only module `adventure_maker/studio_catalogue.py` |
| `dashboard/manifest.json` | declares the backend: `{"name": "hermes64", "api": "plugin_api.py", "tab": {"hidden": true}}` (hidden, so the web dashboard gets no empty tab) |
| `dashboard/plugin_api.py` | backend routes under `/api/plugins/hermes64/` |
| `desktop/plugin.js` | the desktop half: one uncompiled ES module importing only `@hermes/plugin-sdk`, `react` and `react/jsx-runtime`. It is generated by `studio/tools/sync_shared.py`, so edit the sources, not this file. |

The desktop plugin id is `hermes64`, matching the package name, which is how the app names the copied folder `desktop-plugins/hermes64/`.

## Install (first lane's steps; the verified version is `docs/studio/DESKTOP-INSTALL.md`)

1. **Put the package in a local plugins root.** Either install the `hermes64` package as usual, or, while developing, link this checkout so every save re-syncs:
   ```bash
   ln -s /path/to/this/checkout ~/.hermes/plugins/hermes64
   ```
   (The SDK docs: a linked package's `desktop/plugin.js` is watched and hot-reloaded. Catalog and Git installs refresh on **Capabilities → Plugins → Rescan**, on install/update, or on restart.)
2. **Choose the projects folder.** The Studio reads the same setting the hermes64 tools use, `plugins.entries.hermes64.settings.projects_root`: an absolute, existing folder. In `config.yaml`:
   ```yaml
   plugins:
     entries:
       hermes64:
         settings:
           projects_root: /Users/you/Games/hermes64
   ```
3. **Allow the backend half.** Python backend routes are imported only for plugins in the `plugins.enabled` allow-list:
   ```yaml
   plugins:
     enabled:
       - hermes64
   ```
   Then restart the gateway (backend routes mount at startup).
4. **Turn on the desktop half.** Unified-package desktop halves ship opt-in: in **Capabilities → Plugins**, press **Rescan**, then switch on **Hermes64 Studio**.
5. **Open it.** Use the **Studio** row in the sidebar nav, or the **Studio** tab that docks beside SESSIONS | BOTS. Enter on the rack opens the full page on that game.

Expected on first open: your games as box cards (or the empty shelf with NEW GAME). If the backend is off or `projects_root` is unset, the Studio shows "Can't read the shelf" with ENTER Try Again. It never shows a blank page.

To remove it: switch it off in **Capabilities → Plugins** (the desktop half), remove `hermes64` from `plugins.enabled` (the backend), or remove the package folder. Disabling disposes everything the Studio registered and stops any play server.

## What it reads, serves and does (disclosure)

The backend reads:

- the folders directly under `projects_root`, and inside each project only these known files: `.maker/project.json`, `.maker/current.json` and the compiled game it names, `source/spec.json`, `project.json`, the story spec, style profile and `style.lock` it names, `.maker/runs/{check,replay,edit}-*/proof.json`, `replay-*/replay.json`, `playtest-*/report.json` and its PNG frames, `assets-*/assets/report.json`, `export-*/share/{web,macos,windows}` (presence, `FILES.json` sizes), `packs/<id>/pack.json`, `.maker/studio/cover.png`, `.maker/studio/human-playtest.json`, and the cover tool's adopted box art (`project.json` `cover.box`, or `.maker/cover/current.json` and the `box-2x` PNG it names);
- the plugin's own files: `packs/*/pack.json` (style labels and colours) and ten UI sound files from `audio/`.

Every read below `projects_root` is confined (no symlink is followed at any component), bounded in size, and limited to regular files.

The backend serves, to the desktop half only (behind the gateway's normal auth):

| Route | Returns |
|---|---|
| `GET /studio/catalogue` | the catalogue JSON: project-relative paths only, with no absolute paths, user names or timestamps |
| `GET /studio/cover/<id>/<n>/<tag>` | one cover or shot as a PNG data URL, re-derived from disk and checked against its hash |
| `GET /studio/sound/<cue>` | one of ten allow-listed UI cue WAVs as a data URL |
| `GET /studio/folder/<id>` | the project's absolute folder, requested only by an OPEN FOLDER click (the desktop half then calls `ctx.os.revealPath`) |

Side effects happen only on an explicit click:

| Route | Effect |
|---|---|
| `POST /studio/play` | starts one local static server on `127.0.0.1` (random port, random 24-character path token) serving only that game's web export folder, for the SDK's `SandboxedFrame`. It stops on eject, on the next play, or after 30 idle minutes. |
| `POST /studio/stop` | stops it |
| `POST /studio/launch` | macOS only: `/usr/bin/open -n <the export's .app>`, where the .app path is re-derived from the scan (never taken from the request). The desktop half asks first, and the question defaults to NO. |

Chat hand-offs (NEW GAME, EDIT WITH HERMES, EXPORT, REVIEW WITH HERMES) open a fresh chat and place a brief in its composer with `host.composer.setDraft`. The Studio never sends a message. If no composer answers, it copies the brief to the clipboard and says so.

Never: network access beyond 127.0.0.1, downloads, uploads, telemetry, writes to your projects, or reading keys outside its own focused view.

## For developers

```bash
python3 -B studio/tools/sync_shared.py          # regenerate desktop/plugin.js and the file:// bundle
python3 -B studio/tools/sync_shared.py --check  # exit 1 if either is stale (also a unit test)
python3 -B -m unittest tests.test_studio_catalogue -v
node studio/harness/test_shared.mjs             # shared-module unit tests (node is optional)
node studio/harness/run_plugin_harness.mjs /tmp/out   # mock desktop host + real backend functions (31 checks at MERGE4)
python3 -B -m adventure_maker.studio_catalogue /absolute/projects_root   # print a catalogue
```

The prototype runs from `studio/prototype/index.html` over file:// or any static server. Hash parameters drive scenes for screenshots, for example `#sel=thaw&view=detail`, `#catalogue=empty`, `#catalogue=scale&count=300`, `#motion=reduce`, `#input=pad` and `#clock=manual`.

## The mock host (what was tested instead of the real app)

`studio/harness/plugin.html` loads the generated `desktop/plugin.js` in headless Chrome. An import map points the three specifiers at stand-ins: `mock/react.js` (a small local React-like runtime with hooks and keyed reconciliation), `mock/jsx-runtime.js`, and `mock/sdk.js` (area constants, a `SandboxedFrame` with the documented sandbox posture, and a `host` that records calls). `mock_backend.py` serves the API by calling the real `dashboard/plugin_api.py` functions over fixture projects built in the scratch folder: Thaw compiled with a matching proof, a fixture bot verdict and real capture frames, plus a hand-written web page standing in for an export; Last Light compiled and untested; the starter sketch; and a symlinked project that must be skipped.

`run_plugin_harness.mjs` checks 25 things:

- registration of the route, nav row and sessions-zone tab;
- the backend catalogue rendering, with the symlinked project skipped;
- real covers arriving as data URLs;
- the detail view and verdict;
- OPEN FOLDER calling `ctx.os.revealPath` with the right folder;
- PLAY showing a `SandboxedFrame` (`sandbox="allow-scripts"`, no referrer) at a 127.0.0.1 token URL, with a wrong token and traversal both refused, and eject removing the frame and stopping the server;
- NEW GAME opening a fresh chat with the brief in the `new` composer and never calling submit;
- no console errors;
- unmount disposing the DOM;
- the rack listing games and opening the page on the chosen one.

## Not tested in the real app

- Loading in real Hermes Desktop: the real React, the real SDK and the real hot-reload loop.
- Whether `PANES_AREA` with `dock: { pane: 'sessions', pos: 'center' }` really lands as a third tab after Bots for a disk plugin. The bundled Bots plugin uses the same dock plus `enforce: true`, which the Studio deliberately does not set.
- Whether `tabTitleText` is honoured for disk-plugin panes.
- The real `ROUTES_AREA` / `SIDEBAR_NAV_AREA` values and the `game` codicon rendering.
- `host.newChat()` followed by `host.composer.setDraft('new', …)` timing in the real app (the code retries for about 3 s, then falls back to the clipboard).
- A real Godot web export running inside the real `SandboxedFrame`. Its opaque origin has no storage, so browser saves will not persist there, and WebGL2 and audio-worklet behaviour are unverified.
- Native macOS launch of a real exported .app (unsigned local builds may need right-click → Open once).
- The backend under the real gateway: FastAPI wiring, auth and the `plugins.isolation: host` mode.
- A physical gamepad, other displays and DPIs, slower machines, and listening to the sound cues.
- The theme: the Studio deliberately keeps its own palette (it is a world, not a settings page), unlike the SDK's advice to use theme variables. It does not follow light or dark mode.
